# Project Post-Workflow Audit

在工作流/子任务收尾阶段审计执行效果，发现"写了但没做"、"打折做"、"执行效果不佳"的缺陷。

## 触发条件

- 工作流/子任务完成后的收尾阶段
- 用户明确要求审计工作流执行效果
- 项目结束时的工作流效果评估

## 输入参数

| 参数 | 类型 | 说明 | 来源 |
|------|------|------|------|
| `workflow_def` | string (可选) | 工作流定义文件路径 | 用户指定，默认搜索 |
| `project_path` | string (可选) | 项目路径 | 默认为当前目录 |

## 工作流定义格式

技能需要解析 YAML 格式的工作流定义文件。

### 默认搜索顺序

1. `workflow_def.yaml`
2. `workflow.yaml`
3. `docs/workflow/workflow_def.yaml`
4. 当前目录向上搜索

### 定义示例

```yaml
# workflow_def.yaml
name: "子代理驱动开发工作流"
version: "1.0"

description: "用于 PCIE 仿真验证的子代理驱动开发工作流"

steps:
  - id: step1
    name: 计划阶段
    required: true
    sub_steps:
      - 读取任务文档
      - 注入相关经验
      - 生成实施计划
      - 用户审阅通过

  - id: step2
    name: 构建阶段
    required: true
    sub_steps:
      - 分解为独立组件
      - 并行构建
      - 聚合结果

  - id: step3
    name: 验证阶段
    required: true
    sub_steps:
      - Lint检查
      - 仿真验证

  - id: step4
    name: 评估沉淀
    required: true
    sub_steps:
      - 收集执行指标
      - 更新经验文档
      - 填写评估报告

gate_checks:
  - step1: "用户必须审阅通过才能进入下一阶段"
  - step3: "必须同时通过 lint 和仿真"

optional_steps:
  - id: debug_loop
    name: 调试修复循环
    sub_steps:
      - 诊断问题
      - 修复代码
      - 重新验证
```

## 执行流程

### Step 1: 加载工作流定义

1. 根据用户指定的路径或默认搜索顺序查找工作流定义文件
2. 使用 Read 工具读取 YAML 文件
3. 解析提取步骤列表、验收门禁

### Step 2: 收集执行记录

1. 使用 TaskList 工具获取任务系统中的任务状态
2. 识别已完成的任务及其时间戳
3. 记录任务的阻塞关系（blockedBy）

### Step 3: 逐项对比

对于每个工作流步骤，检查：

| 检查项 | 说明 |
|--------|------|
| 步骤是否执行？ | 在任务系统中是否有对应任务 |
| 子步骤是否完整？ | 检查任务描述中的关键动作 |
| 验收门禁是否通过？ | 检查任务完成状态 |
| 执行效果如何？ | 任务是否成功完成 |

### Step 4: 识别缺陷

识别以下三类缺陷：

| 缺陷类型 | 描述 | 识别方法 |
|----------|------|----------|
| 缺失 | 规范要求但未执行 | 任务系统中无对应任务 |
| 打折 | 执行了但不完整 | 任务完成但缺少关键子步骤 |
| 效果差 | 执行了但有问题 | 任务失败或被阻塞 |

### Step 5: 生成报告

生成 Markdown 格式的审计报告，保存到：

```
tasks/evaluations/<workflow_name>_audit_YYYYMMDD_HHMMSS.md
```

**报告结构**：

```markdown
# 工作流执行审计报告

> **工作流**: [名称 v版本]
> **项目/任务**: [名称]
> **执行时间**: [开始 - 结束]
> **审计日期**: [日期]

---

## 1. 执行概览

| 指标 | 值 |
|------|-----|
| 总步骤数 | N |
| 已执行步骤 | X |
| 执行率 | X% |
| 总耗时 | X分钟 |

## 2. 遵循度检查

| 步骤 | 要求 | 实际执行 | 状态 | 备注 |
|------|------|----------|------|------|
| step1 计划 | 必须 | ✓ 完成 | ✅ | |
| step2 构建 | 必须 | 部分完成 | ⚠ | 缺少并行构建 |
| step3 验证 | 必须 | ✓ 完成 | ✅ | |
| step4 沉淀 | 必须 | ✗ 未执行 | ❌ | 经验文档未更新 |

## 3. 缺陷清单

| # | 类型 | 描述 | 对应步骤 | 严重程度 |
|---|------|------|----------|----------|
| 1 | 缺失 | 经验文档未更新 | step4 | 高 |
| 2 | 打折 | 未真正并行构建 | step2 | 中 |

## 4. 效果评估

| 步骤 | 效果 | 说明 |
|------|------|------|
| 计划 | 良好 | 架构图完整，用户已审阅 |
| 构建 | 一般 | 组件完成但未并行 |
| 验证 | 良好 | lint通过，仿真通过 |
| 沉淀 | 差 | 经验文档未更新 |

**综合评分**: X/10

## 5. 改进建议

- [ ] 建议1
- [ ] 建议2

---

**审计结论**: [一句话总结]
```

## 关键原则

1. **通用化设计**: 技能本身不硬编码任何特定工作流，通过 YAML 定义
2. **数据驱动**: 基于任务系统的实际执行记录，而非主观判断
3. **缺陷导向**: 聚焦于发现"写了但没做"的问题
4. **精简输出**: 报告控制在 ~100 行，聚焦核心问题

## 注意事项

- 如果找不到工作流定义文件，提示用户创建或指定路径
- 如果任务系统数据不足，通过用户输入补充信息
- 报告保存前确认目录存在
