# Project Post-Workflow Audit

在工作流/子任务收尾阶段审计执行效果，发现"写了但没做"、"打折做"、"执行效果不佳"的缺陷。

## 触发条件

- 工作流/子任务完成后的收尾阶段
- 用户明确要求审计工作流执行效果
- 项目结束时的工作流效果评估

## 输入参数

| 参数 | 类型 | 说明 | 来源 |
|------|------|------|------|
| `workflow_def` | string (可选) | 工作流定义文件路径 | 用户指定，默认搜索 |
| `project_path` | string (可选) | 项目路径 | 默认为当前目录 |
| `dvv_dir` | string (可选) | DVV 目录路径 | 默认 `.dvv/` |

## 核心审计维度

### 维度 1: 遵循度检查 (Compliance)

检查工作流各步骤是否按规范执行。

| 检查项 | 说明 |
|--------|------|
| 步骤是否执行？ | 在任务系统中是否有对应任务 |
| 子步骤是否完整？ | 检查任务描述中的关键动作 |
| 验收门禁是否通过？ | 检查任务完成状态 |

### 维度 2: 完成度检查 (Completion)

分析 `.dvv/` 目录下各阶段文档，评估输入要求是否在输出中体现。

**文档流向分析**:
```
inputs/ → plans/ → reports/
(输入)     (计划)    (输出)
```

**完成度评估规则**:
| 评分 | 标准 |
|------|------|
| ✅ 完成 | 输出文档明确回应了输入文档中的所有要求 |
| ⚠ 部分完成 | 输出文档回应了部分要求，有关键遗漏 |
| ❌ 未完成 | 输出文档未回应输入要求，或缺失关键输出 |

**检查方法**:
1. 读取输入文档，提取"要求清单"
2. 读取对应输出文档，检查每个要求是否被处理
3. 记录遗漏项和不完整项

### 维度 3: 有效性检查 (Effectiveness)

评估每个阶段的输出是否比输入增加了价值。

**有效性评估规则**:
| 评分 | 标准 |
|------|------|
| 🟢 高 | 输出明显优于输入，增加了新的洞察、决策或可执行方案 |
| 🟡 中 | 输出对输入进行了整理或转化，但价值增量有限 |
| 🔴 低 | 输出基本是输入的复制或简单重述，无明显价值增量 |

**价值增量判断依据**:
- 是否产生了新的结论或诊断？
- 是否提供了可执行的方案？
- 是否降低了问题的复杂度？
- 是否引入了新的风险识别？

## 工作流定义格式

技能需要解析 YAML 格式的工作流定义文件。

### 默认搜索顺序

1. `workflow_def.yaml`
2. `workflow.yaml`
3. `docs/workflow/workflow_def.yaml`
4. 当前目录向上搜索

### 定义示例

```yaml
# workflow_def.yaml
name: "子代理驱动开发工作流"
version: "1.0"

description: "用于 PCIE 仿真验证的子代理驱动开发工作流"

steps:
  - id: step1
    name: 计划阶段
    required: true
    sub_steps:
      - 读取任务文档
      - 注入相关经验
      - 生成实施计划
      - 用户审阅通过

  - id: step2
    name: 构建阶段
    required: true
    sub_steps:
      - 分解为独立组件
      - 并行构建
      - 聚合结果

  - id: step3
    name: 验证阶段
    required: true
    sub_steps:
      - Lint检查
      - 仿真验证

  - id: step4
    name: 评估沉淀
    required: true
    sub_steps:
      - 收集执行指标
      - 更新经验文档
      - 填写评估报告

gate_checks:
  - step1: "用户必须审阅通过才能进入下一阶段"
  - step3: "必须同时通过 lint 和仿真"

optional_steps:
  - id: debug_loop
    name: 调试修复循环
    sub_steps:
      - 诊断问题
      - 修复代码
      - 重新验证
```

## 执行流程

### Step 1: 加载工作流定义

1. 根据用户指定的路径或默认搜索顺序查找工作流定义文件
2. 使用 Read 工具读取 YAML 文件
3. 解析提取步骤列表、验收门禁

### Step 2: 收集执行记录

**来源 A: 任务系统**
1. 使用 TaskList 工具获取任务系统中的任务状态
2. 识别已完成的任务及其时间戳
3. 记录任务的阻塞关系（blockedBy）

**来源 B: DVV 目录文档** (新增)
1. 扫描 `.dvv/` 目录结构：
   ```
   .dvv/
   ├── inputs/          # 输入文档（问题陈述、需求）
   ├── plans/           # 计划文档（调试计划、实施方案）
   ├── reports/         # 输出文档（分析报告、修复记录、验证报告）
   └── workflow_progress_log.md  # 工作流进度日志
   ```
2. 使用 Glob 工具列出各子目录下的文档
3. 按时间戳或命名排序，建立文档流向链

### Step 3: 三维度审计

#### 3.1 遵循度检查 (Compliance)

对于每个工作流步骤，检查：

| 检查项 | 说明 | 数据来源 |
|--------|------|----------|
| 步骤是否执行？ | 在任务系统中是否有对应任务 | TaskList |
| 子步骤是否完整？ | 检查任务描述中的关键动作 | TaskGet |
| 验收门禁是否通过？ | 检查任务完成状态 | TaskList |

#### 3.2 完成度检查 (Completion)

分析 `.dvv/` 目录下各阶段文档的输入输出关系：

**文档配对分析**:
| 阶段 | 输入文档 | 输出文档 | 检查内容 |
|------|----------|----------|----------|
| 问题分析 | `inputs/issue_description*.md` | `reports/analysis_report*.md` | 分析报告是否回应了问题描述中的所有要点 |
| 计划制定 | `reports/analysis_report*.md` | `plans/debug_plan*.md` | 计划是否覆盖了分析报告中的所有修复方案 |
| 修复实施 | `plans/debug_plan*.md` | `reports/fix_record*.md` | 修复记录是否执行了计划中的所有步骤 |
| 验证确认 | `reports/fix_record*.md` | `reports/verification_report*.md` | 验证报告是否覆盖了修复记录中的所有改动 |

**检查方法**:
1. 使用 Read 工具读取输入文档
2. 提取输入文档中的"要求清单"（关键词：需要、必须、应该、要求、问题）
3. 读取对应的输出文档
4. 检查每个要求是否在输出中被回应
5. 记录遗漏项和不完整项

#### 3.3 有效性检查 (Effectiveness)

评估每个阶段的输出是否比输入增加了价值：

**价值增量分析**:
| 阶段 | 期望价值增量 | 判断依据 |
|------|-------------|----------|
| 问题分析 | 根因定位、影响范围评估 | 是否找到了根本原因？是否识别了影响范围？ |
| 计划制定 | 可执行方案、风险识别 | 是否提供了具体步骤？是否识别了潜在风险？ |
| 修复实施 | 代码改动、问题解决 | 是否实际修改了代码？是否解决了问题？ |
| 验证确认 | 确认修复有效、回归通过 | 是否确认了修复有效？是否通过了回归测试？ |

**评分规则**:
- 🟢 高: 输出明显增加了新价值（新结论、新方案、新风险识别）
- 🟡 中: 输出对输入进行了整理，但价值增量有限
- 🔴 低: 输出基本是输入的复制，无明显增量

### Step 4: 识别缺陷

识别以下三类缺陷：

| 缺陷类型 | 描述 | 识别方法 |
|----------|------|----------|
| 缺失 | 规范要求但未执行 | 任务系统中无对应任务，或 DVV 目录缺失输出文档 |
| 打折 | 执行了但不完整 | 完成度检查中发现遗漏项 |
| 效果差 | 执行了但有问题 | 有效性检查评分为低 |

### Step 5: 生成报告

生成 Markdown 格式的审计报告，保存到：

```
.dvv/reports/workflow_audit_report_YYYYMMDD.md
```

（或 `tasks/evaluations/<workflow_name>_audit_YYYYMMDD.md`）

**报告结构**：

```markdown
# 工作流执行审计报告

> **工作流**: [名称 v版本]
> **项目/任务**: [名称]
> **执行时间**: [开始 - 结束]
> **审计日期**: [日期]

---

## 1. 执行概览

| 指标 | 值 |
|------|-----|
| 总步骤数 | N |
| 已执行步骤 | X |
| 执行率 | X% |
| DVV 文档数 | X |

## 2. 三维度评估

### 2.1 遵循度检查 (Compliance)

| 步骤 | 要求 | 实际执行 | 状态 | 备注 |
|------|------|----------|------|------|
| step1 问题分析 | 必须 | ✓ 完成 | ✅ | |
| step2 计划制定 | 必须 | ✓ 完成 | ✅ | |
| step3 修复实施 | 必须 | ⚠ 部分完成 | ⚠ | 缺少 Phase 0.5 |
| step4 验证确认 | 必须 | ✓ 完成 | ✅ | |

**遵循度评分**: X/10

### 2.2 完成度检查 (Completion)

| 阶段 | 输入文档 | 输出文档 | 完成度 | 遗漏项 |
|------|----------|----------|--------|--------|
| 问题分析 | issue_description | analysis_report | ✅ 100% | - |
| 计划制定 | analysis_report | debug_plan | ⚠ 80% | 未覆盖多配置验证 |
| 修复实施 | debug_plan | fix_record | ✅ 100% | - |
| 验证确认 | fix_record | verification_report | ⚠ 75% | 未验证 GEN3 X4 |

**完成度评分**: X/10

### 2.3 有效性检查 (Effectiveness)

| 阶段 | 输入→输出 | 有效性 | 价值增量说明 |
|------|-----------|--------|-------------|
| 问题分析 | 问题→根因 | 🟢 高 | 准确定位 CDC 问题，绘制时钟域图 |
| 计划制定 | 根因→方案 | 🟢 高 | 提供多方案对比，识别风险 |
| 修复实施 | 方案→代码 | 🟡 中 | 执行了修复，但跳过了 Phase 0.5 |
| 验证确认 | 代码→验证 | 🟡 中 | 验证了部分配置，范围不完整 |

**有效性评分**: X/10

## 3. 缺陷清单

| # | 类型 | 阶段 | 描述 | 严重程度 |
|---|------|------|------|----------|
| 1 | 打折 | 计划制定 | 未覆盖多配置验证方案 | 中 |
| 2 | 缺失 | 修复实施 | 跳过了 Phase 0.5 源信号验证 | 高 |
| 3 | 打折 | 验证确认 | 未验证 GEN3 X4 配置 | 中 |

## 4. 综合评估

| 维度 | 评分 | 说明 |
|------|------|------|
| 遵循度 | X/10 | 工作流步骤基本执行 |
| 完成度 | X/10 | 关键输出存在，但有遗漏 |
| 有效性 | X/10 | 价值增量中等 |

**综合评分**: X/10

## 5. 改进建议

### 高优先级
- [ ] 补充 Phase 0.5 源信号验证步骤

### 中优先级
- [ ] 扩展验证范围至 GEN3 X4
- [ ] 更新计划文档覆盖多配置验证

---

**审计结论**: [一句话总结]
```

## 关键原则

1. **三维度审计**: 遵循度、完成度、有效性全面评估
2. **文档驱动**: 基于实际文档产物，而非主观判断
3. **缺陷导向**: 聚焦于发现"写了但没做"、"做了不完整"、"做了没价值"的问题
4. **精简输出**: 报告控制在 ~150 行，聚焦核心问题

## DVV 目录约定

技能默认分析 `.dvv/` 目录，标准结构如下：

```
.dvv/
├── inputs/                     # 输入文档
│   └── issue_description_*.md  # 问题描述
├── plans/                      # 计划文档
│   └── debug_plan_*.md         # 调试/实施计划
├── reports/                    # 输出文档
│   ├── analysis_report_*.md    # 分析报告
│   ├── fix_record_*.md         # 修复记录
│   ├── verification_report_*.md # 验证报告
│   ├── review_report_*.md      # 评审报告
│   └── workflow_audit_report_*.md # 审计报告
├── archived/                   # 归档文档
└── workflow_progress_log.md    # 工作流进度日志
```

## 注意事项

- 如果找不到工作流定义文件，提示用户创建或指定路径
- 如果 DVV 目录不存在，仅基于任务系统进行审计
- 如果任务系统数据不足，通过 DVV 文档补充信息
- 报告保存前确认目录存在
- 文档时间戳用于建立流向链，确保正确的输入输出配对
