# DVV Issue Fix Flow - 代码问题调试修复工作流

## 概述

通用的代码问题调试修复工作流，通过8个阶段子代理完成完整的"问题分析→修复实施→验证闭环"流程。

> **核心原则**: 主代理只控制/编排流程，不做决策，不执行具体任务。所有任务/决策通过子代理执行。

---

## 阶段总览

| 阶段 | 子代理 | 职责 | 输出 |
|------|--------|------|------|
| 0 | 主代理 | 获取用户输入/问题描述 | 问题描述文档 |
| 1 | Subagent A (问题分析) | 详细问题分析 + 调试实施计划 | 分析报告 + 调试计划 |
| 2 | Subagent B (评审) | 评审调试计划，评估遗漏/逻辑问题 | 评审意见 |
| 3 | Subagent A (优化) | 根据评审意见优化调试计划 | 优化后的调试计划 |
| 4 | Subagent C (执行修复) | 执行调试和修复 | 修复后的代码 |
| 5 | Subagent D (验证) | 仿真验证修复，确认无新问题 | 验证报告 |
| 6 | Subagent B (结果评审) | 评估验证结果，决策是否再次修复 | 评审结论 |
| 7 | 主代理 | 总结 + 调用工作流回顾 | 最终报告 |

---

## 通用必须阅读文档

所有阶段（Phase 1-7）**必须**在开始执行前阅读以下文档：

| 文档 | 说明 | 位置 |
|------|------|------|
| 项目 CLAUDE.md | 当前项目的规范 | `{项目路径}/CLAUDE.md` |
| 工作流进度日志 | 工作流执行进度和状态 | `.dvv/workflow_progress_log.md` |

## Phase 0: 获取输入信息

## 主代理职责

1. **收集用户输入**：
   - 问题/缺陷描述
   - 进展/测试报告
   - 相关日志/波形文件
   - 用户期望行为描述

2. **解析输入内容**：
   - 提取关键问题点

   - 确定问题类型（功能/性能/接口等）

3. **创建问题描述文档**：
   ```
   .dvv/inputs/issue_description_{timestamp}.md
   ```

# Phase 1: 问题分析 (Subagent A)

## 职责定义

**问题分析工程师** - 负责详细分析问题，识别根因，制定调试和修复计划。

## 必须阅读的输入文档

| 文档 | 说明 |
|------|------|
| 用户原始输入 | 问题描述、日志、波形文件等（在 `.dvv/inputs/` 下） |

## 调用方式

```markdown
使用 Task 工具启动子代理：
- subagent_type: "dvv-issue-analysis-agent"
- model: "sonnet"
- description: "DVV 问题分析调试"
- max_retries: 3
```

## 必须执行的技能

1. **加载 CLAUDE.md** - 读取当前工作目录的 CLAUDE.md 了解项目规范
2. **project-lesson-loader** - 调用技能获取相关知识索引
3. **project-memory-saver** - 调用技能获取/保存项目知识

## 必须完成的分析任务

### 1. 问题理解
- 理解用户期望行为 vs 实际行为
- 识别涉及的模块/信号/接口

### 2. 根因分析
- 分析代码逻辑
- 检查时钟/复位信号
- 检查信号时序
- 对比协议规范

### 3. 调试计划制定
- 列出需要验证的关键点
- 确定 debug 手段（仿真、波形分析、打印等）
- 制定修复方案

## 输出要求

### 1. 分析报告
```
.dvv/reports/analysis_report_{timestamp}.md
```

必须包含：
```markdown

> **分析工程师**: [代理名称]

[描述用户期望的正确行为]

### 2.2 根因定位
```

# Phase 2: 计划评审 (Subagent B)

## 职责定义

**评审工程师** - 评审调试计划，评估是否有遗漏的现象、更多可行的debug思路、逻辑合理性。

## 必须阅读的输入文档

| 文档 | 说明 |
|------|------|
| Phase 1 分析报告 | 问题分析报告 `.dvv/reports/analysis_report_*.md` |
| Phase 1 调试计划 | 调试计划 `.dvv/plans/debug_plan_*.md` |

## 调用方式

```markdown
使用 Task 工具启动子代理：
- subagent_type: "general-purpose"
- model: "opus"
- description: "DVV 调试计划评审"
- max_retries: 3
```

## 评审检查清单

### 1. 遗漏检查
- [ ] 是否考虑了所有可能的根因？
- [ ] 是否有未考虑的边界条件？
- [ ] 是否有未考虑的异常路径？

### 2. Debug 思路检查
- [ ] 推荐的 debug 手段是否充分？
- [ ] 是否有更高效的调试方法？
- [ ] 是否遗漏了关键信号的检查？

### 3. 逻辑合理性检查
- [ ] 修复方案逻辑是否正确？
- [ ] 是否可能引入新的问题？
- [ ] 是否考虑了副作用？

### 4. 验证方案检查
- [ ] 验证方案是否覆盖所有场景？
- [ ] 是否考虑了回归测试？
- [ ] 是否有 negative test？

## 评审输出格式

```markdown
# 调试计划评审报告

> **日期**: YYYY-MM-DD
> **评审工程师**: [代理名称]

---

---

## 2. 遗漏问题

| # | 问题 | 严重程度 | 建议 |
|---|------|----------|------|
| 1 | 未考虑X信号异常 | 高 | 添加检查X信号的调试点 |

---

## 3. 改进建议

### 3.1 Debug 手段建议
[建议的调试方法]

### 3.2 修复方案建议
[建议的修复方法]

---

## 3. 决策

- 需要优化轮次: [1-3]
- 是否需要重新分析: [是/否]
```

# Phase 6: 结果评审 (Subagent B 复用)

## 职责定义

评估 Phase 5 的验证结果，决策是否需要再次修复。

## 必须阅读的输入文档

| 文档 | 说明 |
|------|------|
| Phase 5 验证报告 | 验证报告 `.dvv/reports/verification_report_*.md` |
| Phase 4 修复记录 | 修复记录 `.dvv/reports/fix_record_*.md` |

## 调用方式

```markdown
使用 Task 工具启动子代理：
- subagent_type: "general-purpose"
- model: "opus"
- description: "DVV 验证结果评审"
- max_retries: 2
```

## 决策标准（必须严格遵守）

### 验证结果分类

| 分类 | 定义 | 决策 |
|------|------|------|
| **全部通过** | 所有验证项通过，原问题已修复，无新问题引入 | 进入 Phase 7 |
| **部分失败** | 原问题已修复，但有边界条件/回归测试失败 | 返回 Phase 4 重新修复 |
| **未通过** | 原问题未修复，或引入严重新问题 | 返回 Phase 1 重新分析 |
| **无法判断** | 验证结果不明确，需要更多信息 | 返回 Phase 4 获取更多信息 |

### 决策检查清单（逐项确认）

1. **原问题验证**: 原问题是否已修复？
   - [ ] 是 → 继续检查
   - [ ] 否 → 返回 Phase 1

2. **边界条件**: 边界条件验证是否通过？
   - [ ] 是 → 继续检查
   - [ ] 否 → 返回 Phase 4

3. **回归测试**: 原有功能是否正常？
   - [ ] 是 → 继续检查
   - [ ] 否 → 返回 Phase 4

4. **新问题引入**: 是否引入新的严重问题？
   - [ ] 否 → 进入 Phase 7
   - [ ] 是 → 返回 Phase 1

## 最大优化迭代次数

**重要约束**: 整个修复循环（Phase 4 → Phase 5 → Phase 6）的最大迭代次数为 **3 次**。

- 第 1 次迭代: 初始修复
- 第 2 次迭代: 第 1 次修复失败后的修复
- 第 3 次迭代: 第 2 次修复失败后的修复（最后一次）

**迭代计数规则**:
- 每次从 Phase 6 返回 Phase 4 计为 1 次迭代
- 达到 3 次迭代后，无论结果如何，必须进入 Phase 7
- 达到迭代上限时，即使验证未通过也终止循环，并在最终报告中说明

## 迭代计数记录

主代理必须在 `.dvv/workflow_progress_log.md` 中记录当前迭代次数：
```
当前修复迭代次数: X / 3
```

# 主代理流程控制

## 流程图

```
Phase 0: 获取输入
    ↓
Phase 1: 问题分析 (Subagent A)
    ↓
Phase 2: 计划评审 (Subagent B) ←──┐
    ↓                              │
Phase 3: 计划优化 (Subagent A) ────┘ (循环1-3次)
    ↓
Phase 4: 执行修复 (Subagent C)
    ↓
Phase 5: 验证 (Subagent D)
    ↓
Phase 6: 结果评审 (Subagent B) ←─────────────┐
    ↓                                       │
[需要再次修复?] → Yes → Phase 4 (迭代+1)      │
    │                    ↓                  │
    │              迭代计数检查 → ≤3次? No → │
    │                    ↓ Yes              │
    └─────────────→ Phase 7 ←───────────────┘
    ↓
Phase 7: 总结回顾 + 工作流审计
```

## 主代理任务清单

1. ✅ Phase 0: 调用 `project-pre-workflow-audit` 准备工作区
2. ✅ Phase 1-6: 串行调用各子代理
3. ✅ Phase 2/3 循环控制: 最多3轮
4. ✅ Phase 6 循环控制:
   - 每次返回 Phase 4 时迭代计数+1
   - 最大迭代次数: 3次
   - 达到上限后强制进入 Phase 7
5. ✅ Phase 7: 调用 `project-post-workflow-audit` 执行审计

## 迭代计数初始化

在 Phase 0 完成后，主代理必须初始化迭代计数器：
```
.dvv/workflow_progress_log.md 中记录：
- 当前修复迭代次数: 0 / 3
```

# 质量保证

## 各阶段验收标准

| 阶段 | 验收标准 |
|------|----------|
| Phase 1 | 分析报告包含问题描述、根因分析、调试计划 |
| Phase 2 | 评审报告包含遗漏检查、改进建议、决策 |
| Phase 3 | 优化后的计划回应了所有评审意见 |
| Phase 4 | 修复记录完整，代码变更已保存 |
| Phase 5 | 验证报告包含功能验证和回归测试结果 |
| Phase 6 | 评审结论明确，决策清晰，迭代计数正确 |

## 工作流完成标准

- 所有阶段执行完成
- 验证通过
- 知识已沉淀
- 工作流审计报告已生成

## 迭代次数验收

- 修复迭代次数不超过 3 次
- 达到迭代上限时，最终报告需说明未完全解决的原因
